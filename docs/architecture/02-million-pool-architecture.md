# 百万账号目标架构

本文描述 v1.0.0 的运行时架构：请求如何路由、选号如何做到常数时间、批量任务如何队列化、
容量如何估算。实现位置以模块名标注。

## 1. 分层

```
                       ┌──────────────────────────────────────────┐
   OpenAI / Anthropic  │  api/ai.py  →  services/protocol/*       │  同步请求（事件循环）
   兼容客户端           │  每请求：取号 → 选出出口 → 调上游 → 记录  │
                       └───────────────┬──────────────────────────┘
                                       │ 1. 取号
                       ┌───────────────▼──────────────────────────┐
                       │ services/account_index.py                │  候选索引
                       │  桶 = (mode, plan, source)               │  O(1) acquire/release
                       │  环形队列 + epoch 惰性失效                │
                       └───────────────┬──────────────────────────┘
                                       │ 2. 账号读写
                       ┌───────────────▼──────────────────────────┐
                       │ services/account_service.py              │  账号池
                       │  _AccountStore（写入钩子）                │
                       │  _by_management_id / _token_order        │
                       │  _selection_index                        │
                       └───────────────┬──────────────────────────┘
                                       │ 3. 持久化
                       ┌───────────────▼──────────────────────────┐
                       │ services/storage/*  (SQLite / PostgreSQL)│
                       └──────────────────────────────────────────┘

   控制台批量操作 ──► services/account_check_queue.py ──► 有界工作线程池
                     （检测 / 刷新 / 同步三条通道，一次一个令牌）
   运维观测       ──► adaptive_governor / proxy_health / dashboard_metrics
```

## 2. 选号索引（`services/account_index.py`）

### 2.1 结构

- 每个账号在**每种模式**（image / text）下最多属于一个桶，桶键为 `(plan, source)`；
- 每个桶维护一个 `deque[(token, epoch)]`，只包含「仍有空闲容量」的令牌；
- `_meta[token] = (epoch, image_bucket, text_bucket)` 记录当前归属；
- `_sizes[bucket]` 维护桶内账号数，用于「有没有可用账号」的 O(#桶) 判断；
- 取号 `acquire()`：从当前游标开始轮转桶 → `popleft` → 校验 epoch 与归属 →
  容量未满则放回队尾，满则移出（记入 `_saturated`），返回令牌；
- `release()`：减少在途；若该令牌在 `_saturated` 且恢复容量，重新入队；
- `rekey()`：AT 轮换时把在途与归属迁移到新令牌，避免「轮换后同一账号被二次租用」；
- `add()`：重新分类只递增 epoch，旧队列项在下次出队时被自动淘汰（惰性删除）。

### 2.2 为什么是常数时间

- 出队是 `deque.popleft()`；
- 重新分类不产生删除成本；
- 忙号不在队列中，跳过的概率与「并发数 / 池大小」同阶；
- 扫描预算（默认 8）封顶单次取号最坏成本，即使整桶都被排除或饱和。

实测（100 万账号，20 万次取号）：p50 2.7µs、p95 4.2µs、p99 5.7µs、24.7 万次/秒。

### 2.3 与账号服务的一致性

`self._accounts` 是可观测的 `_AccountStore(dict)`：

| 操作 | 副作用 |
| --- | --- |
| `store[token] = account` | 更新管理 ID 索引；必要时重新分类；新令牌追加插入序 |
| `del store[token]` / `pop` | 移除管理 ID 索引与调度归属；插入序打洞，空洞过多时压缩 |
| 全量替换（快照刷新） | 重建管理 ID 索引、插入序与整个候选索引 |

只有「状态 / 额度 / 额度未知 / 套餐 / 来源 / 凭据 / 远程检测结果 / 待验证范围」变化才重新分类，
普通计数与时间戳更新不触发，避免每次写回都做一次分类。

## 3. 分页与列表（`api/accounts.py`）

- 无筛选：`iter_account_window(start, stop)` 直接按插入序取窗口，复杂度 O(page)；
- 有筛选（关键字 / 状态 / 分组）：`iter_account_records()` 流式扫描，只投影命中的页码窗口；
  不再为整池创建字典副本；
- 响应页大小上限 10000，前端提供 20/50/100/500/1000/5000 与自定义输入。

## 4. 批量任务（`services/account_check_queue.py`）

- 一个进程内队列，三条通道：`check` / `refresh` / `sync`；取任务时按通道轮转，避免长检测饿死刷新；
- 工作线程数 = `min(用户设置, 调度器生效值)`，随负载自动增减；
- 任务对象只持有 `deque[str]`，一个令牌一个指针；
- 每个工作线程一次只领一个令牌，执行完立刻回到池里领下一个；
- 进度：`processed / failed / skipped / remaining / rate / eta`，错误只保留前 200 条；
- 取消：置位 `cancel`，队列中剩余令牌计入 `skipped`；
- 完成回调把结果写回既有 `refresh_progress` 投影，前端轮询协议不变。

## 5. 出口（`services/proxy_health.py` + `services/proxy_service.py`）

- 每次图片请求结束（成功或连接类失败）把结果写回健康注册表；
- 后台探测器每 120 秒主动探测代理组节点（可手动触发）；
- 连续失败达到阈值 → `down`，冷却时间 60s 起、指数退避至 30 分钟；
- 选出口时过滤 `down` 节点；整组节点全部 down → 该引用降级为直连，不再抛错阻塞请求；
- 成功即恢复 `healthy` 并清空冷却。

## 6. 数据与容量

### 6.1 账号

| 规模 | 内存（账号字典 + 索引） | 建议数据库 | 建议机器 |
| --- | --- | --- | --- |
| ≤ 1 万 | ~50MB | SQLite | 4C/8G |
| 10 万 | ~500MB | PostgreSQL | 8C/16G |
| 30 万 | ~1.5GB | PostgreSQL | 16C/32G |
| 100 万 | ~4-6GB | PostgreSQL | 32C/128G |

说明：账号字典约 1.2-1.8KB/条（含凭据、诊断、配额字段），索引元数据约 200B/条。
上表已含 Python 对象开销与页缓存余量。

### 6.2 吞吐

- 选号：单进程 20 万次/秒以上（不含上游网络）；
- 检测：受上游延迟支配。设单请求 300ms、256 并发 → 约 850 条/秒 → 100 万条约 20 分钟；
- 图片生成：受账号并发（每账号 1-3）与出口并发配额共同约束。

### 6.3 数据库

- SQLite：单写者，适合 ≤5 万账号；必须开启 WAL（默认已开）并定期维护；
- PostgreSQL：>5 万账号推荐；`accounts` 表按 `access_token` 唯一索引；
- 维护：`PRAGMA optimize/ANALYZE/REINDEX/VACUUM/wal_checkpoint` 或 `VACUUM ANALYZE/REINDEX`，
  入口为「设置 → 智能调度与维护 → 数据库一键修复」。

## 7. 请求隔离

| 资源 | 前台请求 | 后台批量 |
| --- | --- | --- |
| 事件循环线程池 | `worker_threads`（默认 128，调度器缩放，下限 32） | 不占用 |
| 账号处理并发 | 仅图片预检占用 1 槽 | `account_processing_concurrency`（无上限，调度器缩放） |
| 账号检测队列 | 不占用 | 独立工作线程池 |
| 出口并发配额 | 每节点 `image_concurrency_limit` | 与前台共享，队列化排队 |

## 8. 失败与降级路径

| 场景 | 行为 |
| --- | --- |
| CPU/内存过载 | 调度器降配（最低到用户设置的 20%），不改变用户配置 |
| 负载恢复 | 连续 300 秒健康后一次性回弹 |
| 单个出口连续失败 | 熔断该节点，切换到同组其他节点 |
| 整组出口不可用 | 回退直连 |
| 上游返回 401/额度耗尽 | 写回账号状态，移出候选池，交给刷新队列 |
| 账号在途已满 | 阻塞等待（有请求级 deadline），不空转全表 |
| 批量任务堆积 | 队列上限拒绝新任务（429），不影响前台 |
| 数据库锁定 | SQLite busy_timeout 30s + WAL；维护时返回明确错误 |
